GWC V49.3 — RAILWAY DRIVE-FIRST FILE STORAGE / LIGHTWEIGHT SERVER PACKAGE
============================================================================

WHAT THIS PACKAGE DOES
----------------------
- Keeps the supplied GWC V49.3 application files, Code.gs, appsscript.json,
  package.json, existing UI, login, settings, and feature code.
- Updates only server.js for Railway deployment and safer static-file serving.
- Adds this report. Existing railway.json, .env.example, and setup guide are kept.
- Railway serves the website from /public only. It no longer exposes the entire
  project root (which contained Code.gs, README files, and configuration files).
- Uses only text/plain parsing for the app's JSON-over-text/plain API requests.
- Keeps resumable Google Drive upload chunk proxy.
- Does not add a Railway database or persistent volume.

WHERE DATA IS STORED NOW
------------------------
1. Main structured app state (students, users, courses, fees, settings, etc.)
   remains in the EXISTING Google Spreadsheet GWC_Storage, located by the
   existing Script Property GWC_SPREADSHEET_ID.
2. File attachments such as notes, PDFs, receipts, and uploaded images use the
   existing Google Drive folder through the existing Apps Script Drive functions
   and resumable Drive upload flow.
3. Railway stores the deployed application code and runs the Node.js proxy.
   No user-uploaded notes/receipts or application database should be stored on
   a Railway Volume by this package.

IMPORTANT DATA-SAFETY LIMIT
---------------------------
This package does NOT migrate the structured GWC_Storage JSON from Google Sheets
into a Drive JSON file. That is a database/backend migration, not a simple storage
setting. Code.gs currently reads/writes the existing Google Sheet, uses sheet
locking, chunked cells, backup sheets, and save verification. Replacing this with
Drive without a designed migration, rollback, concurrency/locking strategy, and
full end-to-end testing risks losing or overwriting student, login, fee, and course
records. Keep the existing Sheet as the database for now. Uploaded files already
go to Drive; this is the safest low-cost split.

RAILWAY SETTINGS
----------------
- Root Directory: repository root (where package.json and server.js are located)
- Build Command: leave Automatic, or npm install
- Start Command: npm start (package.json runs node server.js)
- GWC_API_URL: set to the existing Apps Script Web App URL ending in /exec
- Do not manually set PORT; Railway injects it.
- Do not add PostgreSQL, Redis, or a Railway Volume for this architecture.
- Health check path: /healthz (from railway.json)
- Generate a Railway domain after deployment.

COST NOTES
----------
- A ZIP being 1 MB does not consume 1 MB of monthly outbound bandwidth repeatedly.
- Deploy/build package size is not the same as monthly egress usage.
- The Node process can still consume RAM/CPU while running; this package cannot
  guarantee a fixed monthly bill. Check Railway Usage breakdown for CPU, Memory,
  Network Egress, and Storage.
- Railway Hobby's $5 is a monthly usage credit/minimum plan charge, not 5 GB of
  storage or a 5 GB bandwidth bucket. Any usage above included credit can cost extra.
- Do not add a Volume: persistent volume data remains between months and is billed
  separately; the monthly credit does not clear old files.

SECURITY LIMITATIONS
--------------------
- This update prevents project-root static file exposure.
- It does NOT add server-verifiable HMAC authentication, Apps Script direct-call
  protection, or a website/domain blocklist. The supplied Apps Script backend
  still has the documented V23 baseline security limitation. Do not treat this
  package as fully hardened for sensitive public production use.
- Existing allowed POST actions are preserved. Test all app workflows before
  changing the public domain.

DEPLOYMENT CHECKLIST
--------------------
1. Upload/extract the ZIP contents into the root of a PRIVATE GitHub repository.
   Do not upload the ZIP as a single file.
2. Ensure package.json, server.js, railway.json, and public/ are at repository root.
3. Deploy that repository in Railway.
4. Add GWC_API_URL in Railway Variables using the EXISTING Apps Script /exec URL.
5. Generate Domain and open /healthz; expect JSON with ok:true.
6. Test website, admin/student/teacher login, notes, Drive uploads/downloads,
   fee slips, Meet links, settings, and data persistence.
7. Keep the previous live host until every test passes.

NO LIVE ACCOUNT TESTS
---------------------
Offline ZIP integrity, JSON, and JavaScript syntax can be checked here. This
package has not been deployed to the user's Railway/Google accounts. No live
credentials or existing Sheet data were accessed or changed.
