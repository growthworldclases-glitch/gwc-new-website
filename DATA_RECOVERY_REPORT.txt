6) ROOT CAUSE — EVIDENCE VS HYPOTHESIS
PROVEN:
- At 06:16, both primary and stage had been replaced by the same valid-but-empty 301-character default JSON.
- At 17:56, primary and stage both contained the complete valid 158,203-character payload and exact same SHA-256.
- The original V15 frontend initialized `state` from defaults and, when the server returned no state, explicitly POSTed those defaults to the server. This is a concrete dangerous code path: an empty/failed cloud load could be interpreted as a new database and saved.
- V15 save/poll uses full-state snapshots and does not pass an expected server revision. An old tab can therefore submit an older full state after another portal has changed it.
- V15 backend has a ScriptLock and exact string comparison of staged data, but it does not provide a revision compare-and-swap, per-chunk SHA-256 manifest, or durable transaction pointer/rollback guarantee.

PROVEN DEPLOYMENT CONFIGURATION MISMATCH:
- The URL literal in index.html and the default GWC_API_URL literal in server.js are different (112 characters each; first mismatch at character offset 71). The differing substring is in the Apps Script deployment identifier.
- In the old static/proxy mode, server.js actually sends requests to its own URL; the index.html URL constant is not used by the current fetch path. Therefore the proxy may be pointed at a different Apps Script deployment than the one someone expects from the HTML constant. Whether these deployment IDs belong to the same Apps Script project or separate projects cannot be established offline.
- V17 Apps Script-hosted mode uses google.script.run against the project serving the page, avoiding this split. If legacy proxy mode is retained, set GWC_API_URL to the verified authoritative deployment URL.

NOT PROVEN:
- Whether the exact 06:16 blank write came from the empty-load initialization branch, a stale browser tab, another Apps Script deployment, a manual restore, or a scheduled/other code path. No Apps Script execution logs or deployment inventory were provided.
- Whether the reported chunk-3 same-length mismatch was caused by Sheets cell conversion, concurrent writes, an older writer, Unicode handling, permissions or another runtime issue. The message proves a chunk-content mismatch was detected despite equal total lengths; it does not identify the underlying cause.
- Which deployment ID is the authoritative live project, whether the two deployments share the same Apps Script project/properties, and which deployment owns the active triggers cannot be determined from exported XLSX/ZIP alone.

7) CODE CHANGES IN V17
- Apps Script can serve index.html directly, removing Render/Node hosting dependency for the GAS-hosted mode.
- `google.script.run` bridge added; legacy `/api/gwc` proxy fallback retained.
- Empty cloud state is a hard error; no default database initialization.
- Every save requires `expectedRevision`; stale writes are rejected.
- Core state emptying and >80% core-record reduction are blocked.
- 24,000-character Unicode-safe chunks, per-chunk SHA-256, manifest, total payload SHA-256, JSON validation and exact read-back.
- Staging verifies before primary write.
- Immutable Drive PRECOMMIT and PREPARED snapshots; hourly changed-state snapshots; no automatic deletion.
- Pending commit recovery marker and best-effort rollback.
- Existing login records/state shape, fee-cycle and force-active app code retained.
- Existing `server.js` and `package.json` retained for legacy proxy use.

8) LIMITATIONS
- Offline tests do not prove Google Sheets, Apps Script, Drive or Web App deployment behavior.
- Live spreadsheet restore, Script Properties, deployment URL, permissions, Apps Script execution quotas, trigger authorization, portal logins, Meet URLs and actual backup creation must be verified after deployment.
- Five-year retention is no-auto-delete policy, not a storage guarantee; Google Drive capacity and quotas apply.
- Legacy authentication remains client-side; server-side role/session authorization is a separate production security task.
